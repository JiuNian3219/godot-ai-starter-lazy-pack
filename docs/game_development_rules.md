# 游戏开发专项规范

游戏开发和普通 app 不一样。功能“正确”只是底线，真正的质量还取决于手感、反馈、节奏、资源、帧率、调参效率和试玩循环。

## 0. 阶段门与试玩时机

不要把“能运行”误当成“该评价好不好玩”。当前任务开始前先判断阶段：

- **基础设施**：项目配置、架构、数据形状、场景骨架、工具和自动验证。只做技术验证，不要求试玩或手感结论。
- **普通功能开发**：逐项实现和联调系统。做相称的自动验证；新增或修改玩家交互时，同步检查目标可见性、操作过程和反馈是否符合已确认的体验。AI 先自查并调整，只有需要用户亲手判断的重要差别才安排简短试玩，不要求评价整个游戏是否好玩。
- **垂直切片里程碑**：由用户明确宣布。选取一段可独立体验、能代表最终产品质量的内容；其范围内的核心循环、视觉/UI、声音/反馈、性能基线和关键流程应协同工作。此时组织正式整体试玩；当前功能的交互检查和调参不必等到这个阶段。

垂直切片不是完整游戏，也不是“有一个按钮能点”的 first playable。它是用有限范围证明质量标准与生产管线可行的高完成度样本。没有用户明确声明进入该里程碑时，AI 不得主动要求“验证游戏好不好玩”。

## 1. 核心循环优先

AI 判断玩法功能与核心循环的关系；已有明确结论时直接沿用，只在影响本次方向或范围时向用户说明，不把以下问题变成每次必答的清单：

- 玩家做什么？
- 游戏如何反馈？
- 玩家为什么继续？
- 这个功能是否能在第一版 playable 中体现？

如果功能不能服务核心循环，要谨慎加入。

### 理解体验目标与选择参考

- 先结合项目说明、当前画面、现有操作和已确认 Plan 理解用户要达到的效果。把口语描述转成玩家可感知的画面、操作和结果，明确哪些是已确认要求、哪些只是 AI 的理解；不要先锁定镜头角度、惯性数值或控制算法。
- 对会明显改变体验的不同解释，给出少量具体选择及推荐理由。例如“站在正前方、上面一点”应先讲清观察位置、能看到的主体与操作区域；“挥动很怪”先厘清玩家希望控制方向、位置还是一次动作，以及停止、反向操作和接触目标时的预期。按实际歧义选择问题，不把这些变成固定问卷。
- 目标难以描述、存在尚未确认且影响体验的不同操控方式，或用户反馈效果不对时，主动查找相关游戏、实际操作视频或设计案例，帮助用户选效果后再定实现。通常筛选两三个有实质区别的参考，不凑数量；明确的普通需求直接推进，已确认结论不重复调查。
- 展示具体参考及来源，说明借鉴的部分、操作感差别、代价和对本项目的适配程度。视角优先用截图或示意图，动作优先用视频片段并指出观察位置；不只给作品名称或技术术语。区分实际观察与推测的实现；无法访问或观看时说明限制，不把文字介绍当作已看过动作。
- 选择落实到当前 Plan 和相关行为验收，不自动生成研究报告或总结文档，也不把参考作品的其他功能加入范围。

## 2. 手感和反馈

新增或修改玩家交互时，按当前目标检查相关部分：

- 输入是否带动预期对象；开始、持续、停止或反向操作时，动作是否可控，碰撞与反馈是否对应实际结果。
- 涉及现实工具或身体动作时，握持位置、运动支点、活动范围和接触方向是否合理；拿不准时查实际动作参考，不能仅凭模型跟随或旋转就认定动作成立。
- 惯性、声音、动画、粒子、震动等按体验目标选择；增加惯性可能降低控制精度，反馈强度也不等于质量，不把这些手段统一强加给所有操作。
- 需要调试的数值集中为可调参数。核心操作尚未成立且后续内容依赖它时，先验证最小可操作片段，再扩展相关内容。

AI 先用实际运行、行为检查和必要的画面观察处理明显问题，再报告已经验证的现象。只有仍需亲手判断的重要差别才请用户简短试玩，说明试什么、比较什么，不把每次修改都变成试玩门槛。工具不足或尚未验证的部分如实说明；录制可以检查画面与时序，不能证明真实输入延迟或用户的主观手感。

## 3. 输入与延迟

输入相关要考虑：

- 键鼠、手柄、触屏是否都需要。
- 输入缓冲、连按、长按、释放时机是否重要。
- 动作游戏要考虑 coyote time、jump buffer、attack cancel、hit stop 等机制是否适用。
- UI 输入和 gameplay 输入是否互相干扰。

## 4. 相机

相机通常是游戏体验核心之一。

需要考虑：

- 当前目标、操作区域和关键动作能否看清；工具、角色或 UI 是否遮挡需要观察的部分。按用户期待的观察位置与空间关系选择机位，再确定技术参数。
- 跟随速度。
- 提前量。
- 边界限制。
- 镜头抖动。
- 缩放。
- UI 是否遮挡。
- 宽屏/窄屏是否暴露不该看到的区域。

## 5. 动画和状态

动画不是装饰，它经常决定反馈是否清楚。

需要考虑：

- 状态机是否清晰。
- 动画状态和逻辑状态是否同步。
- 是否存在过渡卡死。
- 攻击/受击/死亡是否有明确时序。
- 是否需要 root motion 或纯代码移动。

## 6. 物理与碰撞

Godot 游戏里碰撞层和 mask 很容易后期混乱。

需要考虑：

- 每个物体属于哪个 collision layer。
- 它检测哪些 mask。
- 是 Area2D/3D、CharacterBody、RigidBody 还是 StaticBody。
- 碰撞形状是否和视觉相符。
- 是否需要调试显示碰撞。

改碰撞层、输入映射、物理参数时，在本次聊天汇报中说明影响。

## 7. 关卡与内容迭代

游戏项目会不断调内容。

需要考虑：

- 测试场景是否足够小。
- 是否有 prototype 场景。
- 关卡资源是否和 gameplay 逻辑解耦。
- 设计师/未来的自己是否能快速调参数。
- 关卡包是否会误引用其他关卡或大资源。

## 8. 资源导入与美术管线

资源不是随便丢进项目就完事。

需要考虑：

- 图片压缩和过滤设置。
- 音频是 stream 还是 sample。
- 模型、贴图、动画的导入设置。
- 像素风是否关闭过滤。
- 大资源是否会进入 shared。
- AI 生成素材是否记录来源和用途。

## 9. 性能预算

游戏有实时帧率要求。

需要考虑：

- 目标 FPS。
- 节点数量。
- `_process` / `_physics_process` 是否过多。
- 是否频繁 instantiate/free。
- 是否频繁加载资源。
- 是否有粒子、灯光、阴影、后处理成本。
- 是否需要对象池或分帧处理。

移动端、Web、低配机器要更保守。

## 10. 调参能力

游戏开发高度依赖调参。

优先使用：

- `@export` 参数。
- Resource 数据。
- 小型调试 UI。
- 测试场景。

避免把手感数值散落在代码里。

## 11. 垂直切片试玩验收

代码验证不等于游戏验收。

只有用户明确进入垂直切片里程碑时，才编写正式人工试玩 checklist：

```text
试玩目标：
操作步骤：
期望手感：
需要观察：
已知问题：
调参项：
```

## 12. AI 完成功能时必须报告

AI 完成游戏功能后按本次相关内容简要说明：

1. 核心循环影响。
2. 当前阶段、本次交互已检查的现象及尚需用户判断的部分；垂直切片才给正式整体试玩计划。
3. 可调参数在哪里。
4. 性能风险。
5. 资源/动画/音效/反馈是否只是占位。
6. 是否需要测试场景或 debug 开关。
