# 工程开发规范

这个文件是 Godot 项目的工程质量总纲。它不是为了限制创作，而是为了避免项目变大后出现“能跑但不可维护、不可拆分、不可测试、不可优化”的问题。

游戏专项规则见：[game_development_rules.md](./game_development_rules.md)。涉及 gameplay、输入、相机、动画、物理、关卡、资源、性能或手感时必须一起看。

## 1. 架构边界

AI 在涉及新增或调整结构时自行判断以下问题；已由代码或 Plan 明确的直接沿用，只向用户说明影响结果或需要取舍的结论，不逐项汇报：

1. 新文件属于哪个模块？
2. 它允许依赖哪些目录？
3. 它应该是组件、Resource、场景脚本、工具脚本，还是纯逻辑脚本？
4. 它是否会让某个场景脚本变成大杂烩？

具体模块和依赖方向见：[architecture_rules.md](./architecture_rules.md)。

## 2. 依赖方向与分包风险

重点关注：

- 共享层不能反向依赖具体 gameplay、UI、关卡或大资源。
- 功能模块之间默认不直接互相引用。
- 大资源不要轻易放进 `shared`。
- 自动加载单例不要持有具体包资源引用。
- 不要为了拿一个值而 `preload` 整个大场景或大资源。

`scripts/audit_dependencies.ps1` 会做轻量检查，但不能完全替代人工判断。

## 3. 玩法逻辑可读性与可审查性

核心目标是让人通过代码理解玩法并验证实现。AGENTS 中的核心要求始终适用；本节用于实现或审查时判断取舍。业务在游戏中包括攻击、奖励、回合、商店、背包等实际行为。

### 顺序与关键规则

在负责行为的实现入口，让条件、关键公式、状态修改和结果可见。阅读顺序接近实际发生顺序；重要中间结果有含义明确的名称，尽量缩小变量生命周期。关键流程不能只剩 `process()`、`execute()` 等含糊调用，也不能散落在顺序不明的信号回调中。

例如下面是一个**假设规则**的结算片段：先计算伤害，再消耗护盾，最后扣生命。它仅说明表达方式，不规定游戏公式。

```gdscript
# 先用护盾吸收本次伤害，再扣除剩余生命伤害。
func apply_hit(attack: int, defense: int, target: Combatant) -> void:
    var damage: int = maxi(1, attack - defense)
    var absorbed_damage: int = mini(target.shield, damage)
    target.shield -= absorbed_damage
    var health_damage: int = damage - absorbed_damage
    target.health = maxi(0, target.health - health_damage)
```

`Combatant` 表示项目已定义且负责该状态的类型，不是引擎内置类型。审查这里时能直接确认公式和先后关系；无需把每一行抽成函数，也不要求把整个战斗系统都放进来。

另一个例子是有序行动。下例约定 `take_turn()` 完成时返回，内部可等待动画或输入，战斗结束后不再轮到下一位：

```gdscript
# 按既定顺序完成每个角色的行动，战斗结束即停止。
func play_round(turn_order: Array[Combatant]) -> void:
    for combatant: Combatant in turn_order:
        if is_battle_finished():
            break
        await combatant.take_turn()
```

不能为缩短代码把这一流程改成同时启动所有角色，或先发出多个信号却未明确等待完成。真实流程如果需要交错执行，应显式表达其时序，而非强制所有行为都串行。

### 封装与控制结构

稳定配置可以合理封装。例如下例把固定敌人场景的实例化集中起来，调用处仍清楚是在生成哥布林：

```gdscript
const GOBLIN_SCENE: PackedScene = preload("res://scenes/gameplay/goblin.tscn")

# 使用已确定的哥布林场景配置，在指定位置生成敌人。
func spawn_goblin(parent: Node2D, spawn_position: Vector2) -> Node2D:
    var goblin: Node2D = GOBLIN_SCENE.instantiate() as Node2D
    # 先确定局部位置，避免 _ready() 观察到尚未配置的位置。
    goblin.position = parent.to_local(spawn_position)
    parent.add_child(goblin)
    return goblin
```

该示例假定资源由当前模块拥有、根节点为 Node2D；实际使用仍需遵守依赖方向和动态节点生命周期约定。封装是否值得取决于是否减少重复知识和理解负担，不以行数或调用次数机械决定。

- 转换、筛选、查找、单一聚合选择含义合适的语言结构；有先后依赖、提前结束或状态变化的过程使用清楚的循环。用实际 GDScript API，不照搬其他语言的方法名。
- 不禁止 `reduce`，也不要求统一函数式写法。检查是否让人同时追踪多个无关结果与可变状态；未经性能证据，不为少遍历一次牺牲表达。
- 模块围绕真实玩法概念与独立机制划分，在既有目录和依赖规则内组织；不要机械叠加 Controller、Service、Manager。保持职责清晰，避免无收益的多层转发。
- 外部数据在入口建立契约，重要状态有明确所有者；真实失败显式处理。不要在每个内部调用重复猜测数据是否有效，也不要靠静默兜底隐藏契约破坏。

## 4. 工程阶段、TODO 与注释

工程阶段决定结构取舍；试玩阶段仍按游戏专项规范执行，两者不要混为同一条固定流程。

- 探索原型聚焦当前问题，不提前搭完整框架；不得因此跳过场景持久化或必要验证。
- 基建先明确已确认的概念、责任、状态归属和数据流，保证当前实现有自然扩展位置；不以快速堆出表面功能代替基础设计。
- 稳定生产沿用已有惯例，局部修改；真实重复机制出现并稳定后再抽象，不能第一次变化就猜最终架构。
- 收尾阶段优先稳定，有明确收益和验证依据才调整结构；涉及已发布存档或外部数据时，在边界处理兼容与迁移。
- TODO 只用于已知但有意延期的事项，说明当前边界、触发条件与未定内容；触发条件满足时重新评估，不自动实现所有候选方向。不用 TODO 代替当前验收项，不创建假想功能空壳。

例如：`# TODO(存档): 当前只保存已确认字段；首个版本迁移需求出现时在加载边界处理，旧字段兼容策略尚未确定。`

中文注释按 AGENTS 执行；测试说明目标、特殊断言与回归风险。注释解释用途、原因和限制，不逐行复述，也不能替代清楚的代码结构。

## 5. 测试与验证

每个功能至少要有一种与当前阶段相称的验证：

- 命令行 smoke test。
- 轻量 SceneTree 行为测试。
- 纯逻辑脚本测试。
- 高风险交互的人工功能冒烟检查（仅在需要时）。
- 已声明的垂直切片里程碑的正式试玩 checklist。
- 后期复杂系统可引入 gdUnit4。

`scripts/verify.ps1` 必须能失败，不允许只打印错误后继续成功。

`scripts/verify.ps1` 检查导入、当前配置的启动场景和依赖，并自动运行 `tests/` 下的 `*_test.gd`。这些轻量 SceneTree 测试自行结束，失败必须非零退出；辅助脚本不使用该命名。没有行为测试时会明确报告，启动冒烟只覆盖最初几帧，不能证明玩法完整正确。

初始场景、主脚本和 HealthComponent 是可替换示例；替换或删除示例时同步调整对应测试，不为通过验证保留旧路径、Title 节点或旧组件。测试断言应对应当前游戏需求。纯逻辑采用确定性测试，重要场景检查实际需要的持久结构。优先轻量测试，已有复杂系统和回归需求足以证明收益时再引入 gdUnit4。

### 运行画面录制

需要检查相机、动画、移动等随时间变化的画面时，调用 Godot 原生 Movie Maker：

```powershell
# 当前主场景，默认 90 帧 / 30 FPS；输出 PNG 序列，AI 可直接读取图片。
powershell -ExecutionPolicy Bypass -File scripts/record_game.ps1
# 指定场景，录制 6 秒游戏时间；场景路径换成项目实际路径。
powershell -ExecutionPolicy Bypass -File scripts/record_game.ps1 -Scene res://scenes/main.tscn -Frames 180 -Fps 30
# 需要视频文件时使用 AVI；相对输出路径以项目根目录为准。
powershell -ExecutionPolicy Bypass -File scripts/record_game.ps1 -OutputFile .tmp/recordings/preview.avi
```

默认产物位于独立的 `.tmp/recordings/` 子目录，命令打印首、中、尾帧路径。按待验证的动作查看相应帧，必要时查看相邻帧或查询运行状态；不能只生成文件就报告验证通过。命令会打开游戏窗口，需要图形环境；不要给录制进程加 `--headless`。文件已存在时拒绝覆盖，换新路径即可。

录制默认只启动场景，不自动点击按钮或移动角色。这是同步的离线录制，可能在 AI 下次工具调用前就已结束；需要交互时，优先在启动前准备临时测试场景来驱动本次动作。只有确认运行时工具已连接到这次录制且进程仍在运行时，才通过外部输入控制它；不要给正式玩法添加录制专用分支。录制按固定帧率推进游戏时间，适合观察视觉顺序，不能证明真实帧率、卡顿或输入延迟；精确等待、结算和提前结束仍用行为断言检查。已查看相关现象且对应验证通过后即可结束，不要求每次修改全面录制。

原生接口与限制见 [Godot 4.7 Movie Maker 文档](https://docs.godotengine.org/en/4.7/tutorials/animation/creating_movies.html)。

## 6. 资源与体积

新增资源时要回答：

1. 资源属于哪个模块？
2. 是否真的需要放到 shared？
3. 是否有压缩、分辨率、导入设置要求？
4. 未来是否可能按关卡、DLC、平台或模式拆包？

大资源进入 shared 前必须说明理由。

保留的 AI 或外部资产随变更登记到 [资产台账](./assets/asset_manifest.xlsx)。记录资源路径、用途、模块、来源或模型、许可证及依据、导入要求、状态和备注；未知来源或许可证标为待确认。生成提示词记录可选，只在复现或继续迭代需要时保留位置；含密钥或个人信息时仅留安全摘要。不要记录缓存与临时截图。台账编辑失败时保留原文件，在聊天中报告未登记信息，不另建台账。

## 7. 性能与手感

游戏不是纯代码项目，但框架和普通功能不应被提前要求评价“好不好玩”。AI 写完后应识别是否已经进入垂直切片；只有在该里程碑才要求人工试玩确认：

- 移动、跳跃、镜头、攻击反馈是否舒服？
- UI 操作是否顺手？
- 是否有明显卡顿、GC、加载延迟？
- 是否有过多常驻节点、自动加载或无意义 `_process`？

## 8. 数据、存档与可调参数

可调参数优先放在：

- exported properties
- Resource
- 配置数据

避免把数值散落在逻辑里。涉及存档时要考虑版本升级和默认值。

## 9. 输入与平台

输入相关改动要考虑：

- 键鼠、手柄、触屏是否需要区分？
- Input Map 是否会影响其他功能？
- 是否需要按平台或设备切换 UI？

不要随便改 `project.godot` 的 Input Map，除非任务明确需要。

## 10. UI 与可访问性

UI 改动要考虑：

- 文案是否清晰。
- 不同分辨率是否会重叠。
- 字体、颜色、交互反馈是否一致。
- 控制器/键盘导航是否需要支持。

## 11. 可观测性与调试

重要系统应该有可调试入口：

- 清晰的错误信息。
- 必要时有 debug overlay 或测试场景。
- 日志不要刷屏。
- AI 修改后要报告如何验证和如何观察问题。

## 12. 审查、提交与交付

遵守 AGENTS 中的验证、作用域提交和聊天汇报要求。审查时能回答：规则在哪里、先后顺序是什么、状态由谁修改、数据从哪里来、哪些失败真实存在、抽象是否减少理解成本。

中大型任务开工说明涉及模块、新文件位置、依赖方向、阶段与验证方式；资源、平台、UI、存档和性能风险按本次范围展开。玩法任务说明核心循环影响与可调参数。

完工在聊天中说明改动、验证结果、剩余风险、必要 Godot 概念和提交 hash。用户要求时才整理说明文档或交接，不自动写经验总结、决策记录或修改长期规则。已有操作说明因本次变更而失真时就地修正。
