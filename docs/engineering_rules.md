# 工程开发规范

这个文件是 Godot 项目的工程质量总纲。它不是为了限制创作，而是为了避免项目变大后出现“能跑但不可维护、不可拆分、不可测试、不可优化”的问题。

游戏专项规则见：[game_development_rules.md](./game_development_rules.md)。涉及 gameplay、输入、相机、动画、物理、关卡、资源、性能或手感时必须一起看。

## 1. 架构边界

每个功能开始前先回答：

1. 新文件属于哪个模块？
2. 它允许依赖哪些目录？
3. 它应该是组件、Resource、场景脚本、工具脚本，还是纯逻辑脚本？
4. 它是否会让某个场景脚本变成大杂烩？

具体模块和依赖方向见：[architecture_rules.md](./architecture_rules.md)。

## 2. 依赖方向与分包风险

重点关注：

- 共享层不能反向依赖具体 gameplay、UI、关卡或大资源。
- 功能模块之间默认不直接互相引用。
- 大资源不要轻易放进 `shared`。
- 自动加载单例不要持有具体包资源引用。
- 不要为了拿一个值而 `preload` 整个大场景或大资源。

`scripts/audit_dependencies.ps1` 会做轻量检查，但不能完全替代人工判断。

## 3. 代码质量

要求：

- 优先使用 typed GDScript。
- 函数职责小，命名清晰。
- 场景脚本负责协调节点，不承载大量业务逻辑。
- 复用逻辑放到组件、Resource 或纯逻辑脚本。
- 不用深层硬编码 NodePath 作为主要架构。
- AI 生成的代码必须让学习者能读懂。

## 4. 中文注释要求

代码需要有简明中文注释，帮助学习和长期维护：

- 自定义函数应有简短中文注释说明作用，纯 trivial 函数可例外。
- 关键 gameplay 逻辑、特殊判定、状态切换、时间窗、可调参数、资源加载假设、性能敏感点必须注释。
- 测试代码要说明测试目标、特殊断言和回归风险。
- 注释应解释“为什么”和“这个逻辑负责什么”，不要把每一行自明代码翻译一遍。

## 5. 测试与验证

每个功能至少要有一种与当前阶段相称的验证：

- 命令行 smoke test。
- 轻量 SceneTree 行为测试。
- 纯逻辑脚本测试。
- 高风险交互的人工功能冒烟检查（仅在需要时）。
- 已声明的垂直切片里程碑的正式试玩 checklist。
- 后期复杂系统可引入 gdUnit4。

`scripts/verify.ps1` 必须能失败，不允许只打印错误后继续成功。

## 6. 资源与体积

新增资源时要回答：

1. 资源属于哪个模块？
2. 是否真的需要放到 shared？
3. 是否有压缩、分辨率、导入设置要求？
4. 未来是否可能按关卡、DLC、平台或模式拆包？

大资源进入 shared 前必须说明理由。

## 7. 性能与手感

游戏不是纯代码项目，但框架和普通功能不应被提前要求评价“好不好玩”。AI 写完后应识别是否已经进入垂直切片；只有在该里程碑才要求人工试玩确认：

- 移动、跳跃、镜头、攻击反馈是否舒服？
- UI 操作是否顺手？
- 是否有明显卡顿、GC、加载延迟？
- 是否有过多常驻节点、自动加载或无意义 `_process`？

## 8. 数据、存档与可调参数

可调参数优先放在：

- exported properties
- Resource
- 配置数据

避免把数值散落在逻辑里。涉及存档时要考虑版本升级和默认值。

## 9. 输入与平台

输入相关改动要考虑：

- 键鼠、手柄、触屏是否需要区分？
- Input Map 是否会影响其他功能？
- 是否需要按平台或设备切换 UI？

不要随便改 `project.godot` 的 Input Map，除非任务明确需要。

## 10. UI 与可访问性

UI 改动要考虑：

- 文案是否清晰。
- 不同分辨率是否会重叠。
- 字体、颜色、交互反馈是否一致。
- 控制器/键盘导航是否需要支持。

## 11. 可观测性与调试

重要系统应该有可调试入口：

- 清晰的错误信息。
- 必要时有 debug overlay 或测试场景。
- 日志不要刷屏。
- AI 修改后要报告如何验证和如何观察问题。

## 12. 长期记忆

需要记录：

- 持久架构/工具/流程选择 -> `docs/decisions/`
- 可复现踩坑 -> `docs/lessons/`
- 长会话交接 -> `docs/session_handoff.md`

## 13. Git 提交规则

每次代码修改任务完成后，默认自动提交代码，除非用户明确说不要提交。

提交前必须：

1. 运行 `powershell -ExecutionPolicy Bypass -File scripts/verify.ps1` 并通过。
2. 检查 `git status` 和 `git diff`。
3. 只 stage 本次任务真正需要提交的文件。
4. 不提交无关用户改动、生成缓存、本地工具、导出产物、`.godot/`、`.tmp/` 或 ignored 文件。
5. 避免无脑 `git add .`；优先使用明确路径，例如 `git add -- scripts/player.gd tests/player_test.gd`。

提交信息使用 Angular/Conventional Commits 规范：

```text
type(scope): short summary
```

常用 type：

- `feat`：新功能。
- `fix`：修复 bug。
- `test`：测试。
- `refactor`：重构。
- `docs`：文档。
- `chore`：杂项维护。
- `perf`：性能优化。
- `build`：构建相关。
- `ci`：CI 相关。
- `style`：不影响逻辑的格式/样式。
- `revert`：回滚。

完成后报告 commit hash。如果因为 Git 身份、仓库状态或验证失败无法提交，必须明确说明原因。

## AI 开工前 checklist

中大型任务开始前，AI 需要先说明：

1. 本次改动涉及哪些模块。
2. 新增文件放在哪里。
3. 依赖方向是否符合规范。
4. 是否涉及资源体积或分包风险。
5. 准备如何验证。
6. 当前是基础设施、普通功能还是垂直切片；只有后两者中确有必要时列出人工功能冒烟检查，只有垂直切片才列正式试玩。
7. 如果是 gameplay 功能，它服务哪个核心循环，哪些手感参数需要调。

## AI 完工后 checklist

完成后需要报告：

1. 改了哪些文件。
2. 验证命令和结果。
3. 是否更新了决策/教训/交接记录。
4. 是否有性能、体积、平台、UI、手感风险。
5. Git commit hash；如果没有提交，说明原因。
6. 下一步建议。
